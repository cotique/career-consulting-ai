# career-consulting-ai — deliberate tradeoffs (not scale/production-hardened)

*Not the same as "deliberately deferred" in ARCHITECTURE.md (that's undecided-yet). These are things we've actively chosen for now, know aren't right at scale, and would otherwise forget once they're working. Each entry: what, why it's fine now, when to revisit.*

## Infrastructure

- ~~**ACR admin credentials (not OIDC/federated identity) for CI push access.**~~ **Resolved**: the deploy authenticates through GitHub OIDC federation with no stored Azure credential, and the app pulls its own image as its managed identity — there is no registry password anywhere. The federated subject is the immutable-id form (`repo:<owner>@<ownerId>/<repo>@<repoId>:ref:...`), which matters because it silently stops matching after a repository is renamed.
- **Postgres reachable from any Azure service, not just ours** (2026-08-10). The Flexible Server firewall uses the "Allow public access from any Azure service within Azure to this server" rule — a `0.0.0.0` rule that admits services in *any* subscription, not only this one. Chosen because the tight alternative is a VNet-integrated Container Apps environment plus private access on Postgres: a subnet, possibly recreating the environment, and hours of work against a credit that expires 2026-09-06. What the rule actually costs is "another Azure service can reach port 5432", not access: behind it sit the admin password, a non-superuser `app_user` role, forced RLS on all eleven tables, and the NFR14 admission list. *Revisit: before the first external user, or at the GCP migration — whichever comes first. On GCP the equivalent would have been private IP + Direct VPC egress.* *(2026-08-15: both triggers are now dead letters — the migration is cancelled and there will be no external user. This tradeoff is therefore permanent rather than temporary, and should be read as a statement about what this deployment always was: a single-user stand behind an admission list, on a firewall rule wider than it needed to be.)*
- **No VNet / `publicNetworkAccess: Enabled` on the Container Apps Environment and ACR.** No need for network isolation with one developer and no sensitive internal traffic yet. *Revisit: if the audience expands beyond dogfooding, or before handling more sensitive data than what's already planned.*
- **ACR Basic SKU** — no vulnerability scanning (Defender for Containers), no private endpoints. Cheapest tier, fine for near-empty registry. *Revisit: before this holds anything beyond a personal-scale image, or if supply-chain risk becomes a real concern.*
- **No mTLS between apps in the Container Apps Environment** (`peerAuthentication.mtls: false`). Moot in the current design — after the 2026-08-09 switch from Temporal to pg-boss there is exactly one app container, and the queue lives inside Postgres (no service-to-service traffic to protect). *Revisit: only if a second in-environment service ever appears.*
- **Single region (Poland Central), no DR/backup strategy beyond Azure platform defaults.** Fine for a personal tool with no uptime commitment to anyone. *Revisit: if this ever needs to be reliable for someone other than the one person running it.*
- **Free-tier Azure subscription** — quota limits, no SLA. *Revisit: if any component needs guarantees the free tier doesn't offer (this will surface as a concrete error, not silently).*

- ~~**Key Vault not provisioned yet**~~ **Resolved at the first deploy**: the vault exists under the RBAC model, the app reads it as its own managed identity, and the deployed container carries no secret environment variables at all — only the vault URL. Locally `.env` remains the sanctioned mechanism, which is the whole point of `SecretsService` having two backends.

## Application

- **28 npm audit findings, all in dev-only tooling** (`@nestjs/cli`, `vite`, `vitest`, `glob`, `tmp`, `picomatch` — build/test tools, not runtime dependencies). The one runtime finding (`drizzle-orm` SQL injection, high severity) was fixed immediately (bumped to `^0.45.2`), not left here. *Revisit: periodically re-run `npm audit`, and before ever exposing any dev-tooling (e.g. Vitest UI mode) on a network — that's specifically flagged as exploitable in the advisories.*

- **Dockerfile runs as root** (no `USER` directive). Cheap to fix, just not done yet. *Revisit: anytime, low effort — do it opportunistically, don't need a trigger.*
- ~~**No API-layer rate limiting**~~ **Done 2026-08-10** (`src/rate-limit`): a global 120 requests/minute, overridden to 10/hour on `POST /onboarding/parse-preview` because that call spends tokens. `/health*` is exempt — the platform probes it continuously, so a limit there would make a healthy deployment report itself unhealthy. Express is configured to trust exactly one proxy hop, without which every request behind the ingress would share a single bucket. **Remaining limitation: the counters are in-process.** With `min-replicas: 0, max-replicas: 1` that is the whole picture; at more than one replica each keeps its own counters and the effective limit multiplies by the replica count. *Revisit: when max-replicas goes above 1 — at which point the fix is a shared store (Redis), which is a dependency worth avoiding until then.*
- **CORS policy undecided.** No frontend exists yet to scope it against. *Revisit: at frontend implementation — must be a specific origin, never `*`.*
- ~~**OAuth token storage mechanism undecided**~~ **Resolved when auth landed**: a signed JWT in an httpOnly, sameSite=lax cookie (Secure in production), never readable by page scripts.
- **Sessions are stateless — they cannot be revoked before they expire.** Chosen so there is no session state to lose across restarts and nothing sticky for the eventual Cloud Run scale-to-zero deployment. Mitigated for the worst case: the auth guard verifies the user still exists on every request, so a deleted account's token stops working immediately. Still missing: signing anyone out of an *existing* account (stolen cookie, "log out all devices"). *Revisit: before external users — that's when revocation and device management start to matter.*
- **Microsoft OAuth not implemented** — Google only. `auth_identities` and the identity service are provider-agnostic, so adding it is a second strategy plus an Entra app registration, not rework. *Revisit: when a user actually needs it.*
- **No provider-linking endpoint** (`POST /auth/link/<provider>`). Moot today: with one provider there is nothing to link, and the identity rule — linking only from an already-authenticated session, never by matching email — is what the endpoint would have to obey. *Revisit: together with the second provider, not before; building it now would mean an untested authorization path guarding nothing.*
- ~~**Prompt-injection handling for user-supplied text (vacancy/resume content) not yet designed into the LLM abstraction layer.**~~ **Resolved in the LLM layer**: the request shape structurally separates trusted `instructions` from untrusted `userContent`; the single rendering path (`src/llm/prompt-render.ts`) wraps untrusted text in delimited data blocks with a standing data-not-instructions notice, and neutralizes smuggled delimiters. Regression-tested.
- **Blob soft-delete and versioning are off** (2026-08-10). Azure recommends both, and both would let a deleted resume survive a deletion request for the length of their retention window — which turns FR5 into a promise the system does not keep. Off is the deliberate choice while no post-restore re-deletion procedure exists. *Revisit: together with database backup retention, which owes exactly that procedure — the same hole in another store. Turn them on only alongside it, never "for safety" on their own.*
- **No finite retention period for user content** — kept until deleted (NFR16). Fine while the only person's data in the system is the developer's own. *Revisit: before the first external user, where "we keep it forever unless you ask" stops being a defensible answer.*
- **Uploaded files are not scanned for malware**. Single user uploading her own documents; the file is stored and read back, never executed. *Revisit: before the first external user — an upload endpoint that accepts arbitrary files from strangers is a different proposition.*
- **Upload type is decided by the type the client declares** (found 2026-08-12 while testing the deployed app by hand). The check has both failure directions at once, which is why it is recorded rather than left as "it works": a *truthful* client that omits the type is refused — a real `.docx` uploaded with `curl` arrives as `application/octet-stream` and gets a 400 — while a *dishonest* one is not constrained at all, because the sender writes the header. So it is inconvenient for honest callers and no protection against the others. The fix is to read the leading bytes (`%PDF`, and `PK\x03\x04` for a docx, which is a zip) and treat a mismatch with the declared type as the refusal, rather than trusting either alone. Not done now because it wants its own tests and the upload path is already merged and deployed. *Revisit: before the first external user, together with the malware-scanning entry above — the same trust boundary, and the same moment it stops being theoretical.*
- **Resume extraction runs synchronously rather than as a job**, against ARCHITECTURE's own rule (a slow, failure-prone, expensive-to-redo LLM call over a large document is job-shaped). no queue exists yet, and inventing a temporary one would be worse than waiting. Mitigated by shape rather than hope: the work lives in `extractResume(userId, resumeId)`, taking identifiers only — exactly a job handler's signature — so a queue could wrap it without a rewrite. *Revisit: whenever a queue is introduced.*
- **Static LLM price table** (`src/llm/pricing.ts`) can drift from actual provider pricing — `cost_estimate` and the budget cap would silently skew. *Revisit: whenever a model is added/changed in `task-config.ts`, and occasionally against the provider's published prices.*
- **LLM inference is not EU-resident.** Personal data (resume text, vacancy notes, free-text answers) is sent to the Anthropic first-party API, which routes globally by default. Investigated rather than assumed (2026-08-09): the `inference_geo` request parameter accepts only `us` and `global` — **there is no EU value on any model** — and it is supported from Claude 4.6 onward, so on Haiku 4.5 it is a 400. Switching to a model that accepts it would cost 3x per token and still not yield EU residency, so it was not done. The real EU path is a different provider surface: Google Vertex exposes an `eu` multi-region endpoint (`aiplatform.eu.rep.googleapis.com`) that keeps inference inside the EU, carries Haiku 4.5, and costs +10% — a second `LlmProvider` implementation plus a GCP project and service-account auth, which is exactly what the provider abstraction exists for. *Revisit: before any person other than the developer has data in the system — while it is one person processing her own data this is a documentation gap, not a transfer problem. Verify Haiku availability on the `eu` endpoint at that point; regional model availability differs from the global list.*
- **No prompt caching in the LLM layer.** Deliberate: current prompts are far below Haiku 4.5's 4096-token cacheable minimum and calls are sporadic (no prefix repeats within the 5-minute TTL), so cache_control would be a silent no-op today. *Revisit: when batch flows land (ATS polling scoring many vacancies against the same resume/profile context) — that's when a shared prefix gets big enough and repeats enough to pay.*

## Process

- ~~**No deployment to Azure until auth is complete**~~ — **condition met 2026-08-09**, when sign-in, the per-request RLS context and the account routes landed; admission control (NFR14) then closed the "anyone who reaches the URL becomes a user" hole on 2026-08-10. Everything the gate was holding back is in place: the vault, a health endpoint split from readiness, rate limiting, `AUTH_ALLOWED_SUBJECTS` set and `ENABLE_SWAGGER` left off. **Migrations are still run by hand from a workstation** — which keeps the database firewall narrow rather than opening it to CI runners, and the property that protects a deploy is the expand/contract rule, not the pipeline. Local development still uses docker-compose (Postgres + Azurite).
